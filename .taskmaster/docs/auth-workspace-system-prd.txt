# Grid Brain - Workspace Management & Enhanced Authorization System
## Product Requirements Document (UPDATED)

# Overview  
Grid Brain ha già un sistema di autenticazione Magic Link funzionante e basic project-level authorization. Ora necessita di un sistema di **workspace multi-tenant** e **gestione avanzata utenti** per supportare crescita aziendale e gestione clienti esterni.

**Stato Attuale (GIÀ IMPLEMENTATO):**
- ✅ Magic Link Authentication completo (backend + frontend)
- ✅ Dual user system: TeamMember (@thegridcompany.it) + User (app)
- ✅ Basic project authorization con ProjectMember roles
- ✅ Frontend auth flow con protected routes
- ✅ JWT token management e refresh

**Problema da risolvere:** Mancano funzionalità per scalare l'applicazione:
- **Workspace multi-tenant** - isolamento dati per organizzazioni diverse
- **Unified user management** - admin dashboard per gestire utenti
- **User invitation system** - onboarding automatico nuovi utenti
- **Enhanced permissions** - controllo granulare risorse per workspace
- **Client external access** - accesso limitato progetti per clienti

**Target Users:**
- Super admin (Paolo) - gestione completa sistema + multi-workspace
- Admin workspace - gestione team proprio workspace
- Utenti esistenti - switch between workspace quando applicabile
- Clienti esterni - accesso limitato ai loro progetti

**Valore:** Trasformare Grid Brain da tool interno a piattaforma scalabile per multiple organizzazioni mantenendo security e UX.

# User Experience  

## User Personas

### 1. Super Admin (Paolo, CTO)
- **Obiettivi:** Controllo completo sistema, gestione workspace multipli
- **Pain points:** Necessità visibilità totale, gestione sicurezza
- **Features principali:** Dashboard globale, gestione multi-workspace, analytics sistema

### 2. Admin Workspace (Project Manager)
- **Obiettivi:** Gestire team del proprio workspace, assegnare progetti
- **Pain points:** Coordinare team, controllare accessi progetti
- **Features principali:** Gestione utenti workspace, assegnazione permessi progetti

### 3. Developer/Employee
- **Obiettivi:** Accesso veloce ai propri progetti, collaborazione team
- **Pain points:** Login veloce, trovare informazioni rilevanti
- **Features principali:** Dashboard personalizzata, notifiche, accesso progetti assegnati

### 4. Client Esterno
- **Obiettivi:** Monitorare stato progetti, comunicare con team
- **Pain points:** Accesso semplice, informazioni chiare progresso
- **Features principali:** Vista limitata progetti, comunicazione, reportistica

## Key User Flows

### 1. First-Time Access Flow
```
Non-authenticated user → Landing page → Redirect to login → 
Email input → Magic link sent → Email click → 
Auto-login → Role-based dashboard redirect
```

### 2. Daily Access Flow
```
Returning user → URL access → Check auth → 
If valid: Dashboard redirect | If expired: Login flow
```

### 3. Admin User Management Flow
```
Admin dashboard → User management → Add user → 
Send invite → User receives email → Registration flow → 
Admin assigns roles/workspace → User active
```

### 4. Workspace Switching Flow (Multi-workspace users)
```
Dashboard → Workspace selector → Switch workspace → 
Context change → Dashboard refresh with new data
```

## UI/UX Considerations
- **Login Page:** Minimalista, solo campo email + CTA chiaro
- **Dashboard:** Layout modulare basato su ruolo utente
- **Navigation:** Breadcrumb + sidebar con permessi-based menu items
- **Workspace Indicator:** Header sempre visibile con workspace corrente
- **Mobile Responsive:** Login e dashboard principale responsive
- **Loading States:** Skeleton loading per tutti i componenti dati

## APIs and Integrations

### Authentication Endpoints
```
POST /api/v1/auth/login           # Magic link request
GET  /api/v1/auth/verify/{token}  # Magic link verification
POST /api/v1/auth/logout          # Logout
GET  /api/v1/auth/me              # Current user info
```

### User Management Endpoints
```
GET    /api/v1/users                    # List users (admin)
POST   /api/v1/users                    # Create user (admin)
GET    /api/v1/users/{id}               # Get user
PUT    /api/v1/users/{id}               # Update user
DELETE /api/v1/users/{id}               # Delete user (admin)
POST   /api/v1/users/{id}/invite        # Send invite
PUT    /api/v1/users/{id}/role          # Update role (admin)
```

### Workspace Endpoints
```
GET    /api/v1/workspaces               # List user workspaces
POST   /api/v1/workspaces               # Create workspace (admin)
GET    /api/v1/workspaces/{id}          # Get workspace
PUT    /api/v1/workspaces/{id}          # Update workspace
DELETE /api/v1/workspaces/{id}          # Delete workspace
POST   /api/v1/workspaces/{id}/switch   # Switch current workspace
```

# Risks and Mitigations  

## Technical Challenges
**Risk:** Complessità multi-tenant data isolation
**Mitigation:** Start con Row Level Security PostgreSQL, pattern provato + documentazione chiara

**Risk:** Frontend state management per auth/workspace context
**Mitigation:** Use React Context + local storage, keep it simple initially

**Risk:** Email deliverability per magic links
**Mitigation:** Use transactional email service (SendGrid/AWS SES), implement retry logic

## MVP Definition
**Risk:** Breaking existing functionality
**Mitigation:** 
- Phase 1 focus: additive changes only, no breaking changes
- Maintain existing auth flows (TeamMember magic link + User password)
- Default workspace assignment per existing users
- Incremental rollout workspace features

**Risk:** Data migration complexity
**Mitigation:**
- Start con single default workspace ("The Grid Company")
- Associate existing projects/data to default workspace
- Test migration scripts in staging extensively

## Resource Constraints
**Risk:** Tempi sviluppo frontend + backend
**Mitigation:** 
- Start backend-first con mock frontend
- Use component libraries (MUI/Chakra) per UI velocity
- Prioritize core flows over edge cases

**Risk:** Testing complexity multi-tenant system
**Mitigation:**
- Unit tests per auth logic
- Integration tests per permission flows
- Staging environment con multiple workspace test

## Research Findings
- **✅ Magic Link Auth:** Already implemented successfully, following Shopify/Notion patterns
- **Multi-tenant Patterns:** Row Level Security PostgreSQL for data isolation (proven pattern)
- **React State Management:** Zustand already used for auth, extend per workspace
- **Workspace UI Patterns:** Slack, Discord, Notion workspace switchers for UX reference
- **Invitation Systems:** GitHub organization invites, Slack workspace invites for workflow inspiration

## Technical Specifications
- **✅ JWT Expiry:** 24h access token (già implementato, no refresh token pattern)
- **✅ Magic Link Expiry:** 15 minuti (già implementato)
- **Enhanced JWT Payload:** Add workspace_id field to existing token structure
- **✅ Database:** PostgreSQL con vector extension (già setup)
- **Row Level Security:** Enable RLS policies per workspace isolation
- **Workspace Slug Pattern:** lowercase, alphanumeric + hyphens only

## Security Considerations
- **OWASP Compliance:** Input validation, CSRF protection, XSS prevention
- **Rate Limiting:** 5 magic link requests per hour per email
- **Audit Logging:** All admin actions logged con timestamp + user
- **Data Encryption:** At rest + in transit, PII hashing dove possibile

## Performance Targets
- **Login Flow:** <3s end-to-end magic link generation
- **Dashboard Load:** <2s initial load con skeleton states
- **Permission Check:** <100ms per API call
- **Workspace Switch:** <1s context change

## Compliance Notes
- **GDPR:** User data deletion support, consent tracking
- **SOC2:** Audit logging, access controls, data encryption
- **Privacy:** Minimal data collection, clear privacy policy
